GazeSync 本轮具体审查意见
2026-10-17；审查对象为 0.4.0，明确的软件修复进入 0.4.1。

判断
当前材料适合作为软件实现技术报告。若按 CHI 完整研究论文评估，最需要补的是特定使用条件下的证据，而不是增加更大的研究叙事。下面的实验建议尚未执行，也没有被写成已完成结果。四位作者和既定标题保留。

R1 优先级高：当前对照不能衡量相对原 GazeSync 的收益
位置：Section 2.1、4.3、7.3；Figure 2、4A。
事实：原系统描述了 50 ms 容差的 nearest-state merge，而实验只把 capture-time join 与刻意使用 receipt-time frame 的策略对比。
问题：54.4–79.6 px 的残差可以说明错误关联的后果，不能说明相对原系统或正确离线重建流程改善多少。
建议：在同一记录上增加原系统可复核的近邻/容差策略、capture-time join 和 receipt-time 策略；分别报告错误关联数、无匹配/歧义比例和空间误差。先确认原代码的 tie、容差和回调时间定义，再实现；不能仅凭一句描述冒充原系统复现。

R2 优先级高：800 ms 单种子矩阵未覆盖论文讨论的持续运行问题
位置：Section 7.2、8；paper/data/validation.json。
事实：78 个 rate/context case 均为 800 ms、seed 41；交互场景是 9 秒、三个种子。短矩阵不会触及默认 100,000 条原始记录上限，也难以观察时钟漂移；部分频率诊断需要约一秒的窗口。
问题：高频配置通过不能被读成高频长期采集已经稳定。
建议：增加一个可复现的 10–30 分钟离线压力轨迹，覆盖实际的 rollover、延迟积压、断流/恢复和多 surface；报告 pending 峰值、丢弃计数、批处理耗时 P50/P95/P99、内存及导出体积。该压力测试与 78 个短正确性 fixture 分开报告。

R3 优先级高：保留样本的误差需要与可用率一起报告
位置：Section 6.2、7.3；Table 3。
事实：usable 会排除 blink、缺历史、歧义和部分坐标失败；当前主表强调全记录收到、frame mismatch 和最大浮点残差。
问题：收到样本不等于得到可用的内容坐标。只看可重建子集的近零残差，可能掩盖大量样本被排除的情况。
建议：把 expected/received、mapped、usable、ambiguous 和 missing-history 明确分开；错误按其分母标注。增加固定运动下 uncertainty × delay 的小型敏感性表，并报告阈值改变造成的覆盖率变化。

R4 优先级中：Figure 4B 与 Table 3 信息重复，研究用途不清
位置：Figure 4B。
事实：该图是 78 个 case 的最大 Python–TypeScript 浮点差异 CDF，横轴为 10^-13 px；Table 3 已给出最大值。
问题：它证明算术一致性，却不能帮助读者选择采样率、延迟预算或有效性阈值。
建议：保留表中的数值一致性结果，将此图移至补充材料；主图改为 R3 的误差—覆盖率关系，或 R2 的延迟/内存测量。新图必须由新增实验生成，本轮没有更换成虚构结果。

R5 优先级高：moving-phone 的 pose-age 检查不是几何误差界
位置：Section 5.6、9；Figure 3。
事实：ray 与平面需共享时刻，但实现使用已选 presentation 的 pose，并检查其 age；模拟在帧间保持 pose。Figure 3 是已知的合成标定布局。
问题：即使 pose age <50 ms，快速转动时交点也可能偏移明显；图中精细的 3D 渲染不能提供物理标定准确性证据。
建议：至少增加固定 gaze/plane 条件下的已知平移和旋转速度实验，比较精确采样姿态、保持姿态与设置的 age 阈值。若要主张真实端到端能力，还需独立目标、显示时序参考和设备测量；否则保持技术报告现在的明确限制。

R6 优先级中：与现有工具的关系缺少可核对的功能比较
位置：Section 2.2。
事实：目前主要讨论 LSL 和一篇 gaze pan/zoom 研究，SDK 文档用于解释坐标。
问题：读者不容易判断新增的是采集能力、时钟估计、二维刺激变换日志、三维投影还是跨语言回放。
建议：只选两三个最相关系统，逐项核实 capture timestamp、presentation history、2D/3D、独立双眼、回放和发布状态；没有证据的格子记为未验证，不写成不支持。避免把 LSL 的传输/时钟层与本项目的内容坐标层当作同类替代品。

R7 优先级中：方法章节混入较多开发历史
位置：Section 5.4–5.5、7.1。
事实：正文叙述“旧实现得到 (500,300)”以及多项修复过程；Section 5 的坐标教学占较大篇幅。
问题：读者需要先理解最终可用的契约和适用条件；修复历史会分散主线。
建议：保留正确的 (860,460) 独立例子与关键坐标表；把旧错误、完整矩阵推导和详细 audit 列表移到附录或仓库。正文增加一个短的研究者接入例子，说明输入、presentation 调用、flush watermark 和最终记录分别来自哪里。

R8 优先级中：阈值和默认参数缺少选择依据
位置：Section 4.2、5.6、5.7、8。
事实：默认 reorder 60 ms、clock uncertainty 8 ms、pose age 50 ms、pair skew 5 ms 和 confidence 0.6；文中承认它们可配置。
问题：多个设备提供的 confidence 含义不同；目前尚无敏感性证据支持默认值适用于这些设备。
建议：把默认值称为软件初始配置，给出每个参数的单位、阻断行为与调整依据；优先评估 clock uncertainty/reorder/pose age，而不是把所有参数组合成庞大网格。保留 confidence=null 的当前处理。

本轮已实际修复和准备

1. 两种实现均可复现一个 pending 去重漏洞：maxRecords=2、maxPending=8，依次传入 a、b、c、a，旧代码接受了两条尚未处理的 a。新增 pending 身份集合后，滚动的 recent-ID 缓存不再解除 pending 保护；拒绝重复时状态不变。
2. Python 原始记录缓冲区的 pop(0) 改为 deque.popleft；公开 records 和 JSON 仍为有序、独立的 list 快照。优化范围仅为原始记录保存，未声称完成 TypeScript/ring buffer 或流式存储。
3. 发布检查原来没有比对 Python 的运行时 version.py 与 npm lock/schema 版本，现在已补齐，防止包声明版本和记录内版本分离。
4. 新增最小 Overleaf ZIP 工具与双向本地同步工具。同步默认预览，目标存在并行修改时拒绝覆盖；不操作账号、凭据或 Git 网络。
5. 论文只更新实现版本、去重窗口和存储实现的准确描述。上面的对照、压力测试、实体设备测量和改图仍是讨论事项。

建议本轮讨论顺序
先决定按“软件技术报告”还是“CHI 研究论文”组织稿件；两者都可先完成 R1 与 R3 的小型对照和覆盖率报告。再决定 R2 的运行时测量，以及 R5 是否需要实体设备证据。最后精简坐标推导和调整 Figure 4B。
